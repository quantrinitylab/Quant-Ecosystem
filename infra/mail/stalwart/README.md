# Stalwart lab: configuration as code

Mail engine of the QuantMail lab: [Stalwart](https://stalw.art) (AGPL-3.0 Community edition, unmodified image).
We only write glue here. Nothing in this folder implements SMTP, IMAP, JMAP or spam logic.

Lab domain: `lab.quantrinity.in`, host `mail.lab.quantrinity.in`. No real mail domain is involved.

## How configuration is applied (v0.16 model, not the old TOML files)

Since v0.16 there is no big `config.toml`. Stalwart reads one small startup file, `config.json`
(only the data store location), and keeps **every other setting as an object in its database**, managed through
the JMAP management API. For configuration as code the project provides `stalwart-cli apply`, which takes an
NDJSON plan of idempotent `upsert` / `update` operations (docs: Configuration > Declarative deployments).

This folder therefore holds:

| File | Purpose |
|---|---|
| `bootstrap.json.tmpl` | First start only: the `Bootstrap` object (hostname, default domain, RocksDB on the data volume, console logging, DKIM key generation, manual DNS). Applying it writes `config.json` and creates the administrator. |
| `plan/*.ndjson.tmpl` | The rest of the configuration, one concern per file. `provision.sh` renders the chosen files from `.env` (only a fixed list of variables is substituted) and pipes them to `stalwart-cli apply --stdin`. Re-running is safe. |
| `provision.sh` | `bootstrap`, `apply`, `all`, `dns`, `status`. |
| `docker-compose.yml` | Stalwart, the hooks stub, optional Postgres (`sqldir` profile), the one-shot CLI (`tools` profile). |

Secrets are never written into a plan. Plans refer to them with Stalwart's `EnvironmentVariable` secret type
(`CLOUDFLARE_DNS_TOKEN`, `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, `RELAY_PASS`, `PG_PASSWORD`); the container
gets them from `stalwart/.env` (mode 600, git-ignored, VM only).

| Plan file | Selected by | What it configures |
|---|---|---|
| `10-tls-dns01` / `10-tls-http01` | `ACME_CHALLENGE=Dns01\|Http01` | ACME provider (Let's Encrypt), certificate for the lab domain plus `mail.` SAN, DKIM management (RSA-2048 and ed25519, generated by the server, rotated by it), Cloudflare DNS server for DNS-01. HTTP-01 adds a listener on port 80 and keeps DNS manual. |
| `20-listeners` | always | Adds `submission` on 587 (STARTTLS). Stalwart's first start already creates 25, 465 (implicit TLS), 993, 995, 4190, 443 and 8080. |
| `30-storage-r2` / `30-storage-local` | `STORAGE_BLOBS=r2\|local` | S3 blob store on Cloudflare R2 (custom endpoint, region `auto`) or blobs in the embedded DB on the data volume. |
| `40-accounts-internal` / `45-directory-sql` | `DIRECTORY=internal\|sql` | Internal directory with `alice` and `bob`, or a SQL directory against the Postgres users table. |
| `50-outbound` | always | Relay route `relay` and the outbound route expression: local domains deliver locally, everything else goes to `OUTBOUND_ROUTE`. |
| `60-spam` | always | Spam filter settings written out explicitly (enabled, spam threshold 5.0, built-in rule set). |
| `70-hooks` | always | A webhook (delivery, queue, ingest and report events) and one MTA Hook (stages `rcpt` and `data`), both to the `hooks` stub. |
| `80-lab-throttles` | `LAB_RELAX_THROTTLES=1` | Lab only: raises the default inbound throttles so the 2,000 message load test can run. |
| `90-reload` | always | `ReloadSettings` action (listeners, routes and expressions are read once into a snapshot). |

### DKIM

`dkimManagement` is `Automatic` with both algorithms. Stalwart generates an RSA-2048 and an ed25519 key and keeps the
private keys in its database. No private key is in this repository. Public keys are published by Stalwart
itself (the plan limits its automatic DNS publishing to the `dkim` record type), or by `lab/dns-lab.ps1` from
`./provision.sh dns` output.

## Runbook (on the VM, in `infra/mail/stalwart`)

```bash
cp ../.env.example .env && chmod 600 .env     # then fill in the SECRET values
./provision.sh all                            # bootstrap + apply
./provision.sh status
./provision.sh dns > /tmp/zone.txt            # zone file with MX, SPF, DKIM, DMARC suggestions
```

The administrator created by bootstrap is written to `stalwart/.rendered/admin.env` (mode 600). Copy it to your
secret store and keep it out of the repo. `provision.sh bootstrap` is a no-op once `config.json` exists.

Admin web UI: `https://mail.lab.quantrinity.in/admin`. The plain HTTP admin listener (8080) is published on the
VM loopback only; reach it through an OCI Bastion port-forwarding session.

## Storage: R2 and the local-disk fallback

* `STORAGE_BLOBS=r2`: set `R2_ENDPOINT` (`https://<account>.r2.cloudflarestorage.com`), `R2_BUCKET`
  (`quantmail-mailblobs`), `R2_ACCESS_KEY_ID`, `R2_SECRET_ACCESS_KEY`, then `./provision.sh apply`.
  Region is the custom region name `auto`. R2 keeps its durability contract, so `verifyAfterWrite` could be turned
  off later to save a request per write; the lab leaves the safe default.
* `STORAGE_BLOBS=local` (default): blobs stay in the embedded RocksDB on the `stalwart-data` volume. Use this when
  R2 is not ready or fails. Metadata, queue and settings are always on the volume.
* Switching the blob store does **not** move existing blobs. In the lab this is acceptable (test mail only); do the
  switch before any real data exists.

## Outbound routing: relay now, direct later

Oracle blocks outbound port 25 by default, so the lab sends through a smart host on port 587
(`RELAY_HOST`, `RELAY_PORT`, `RELAY_USER`, `RELAY_PASS`; STARTTLS is negotiated when offered).

**One-line change to direct delivery:** set `OUTBOUND_ROUTE=mx` in `.env` and run `./provision.sh apply`.
(The route expression becomes `local` for local domains, otherwise `mx`. The relay route stays defined and unused.)

## Alternative directory: the Quant users table in Postgres

```bash
echo 'PG_ADMIN_PASSWORD=...' >> .env && echo 'PG_PASSWORD=...' >> .env    # long random values
docker compose --profile sqldir up -d postgres
../lab/seed-sql-directory.sh                    # creates the fixture users carol and dave
sed -i 's/^DIRECTORY=.*/DIRECTORY=sql/' .env && ./provision.sh apply
```

Plan `45-directory-sql` points `Authentication.directoryId` at an SQL directory with queries on the views
`stalwart_accounts`, `stalwart_emails`, `stalwart_group_members` defined in `../lab/postgres-fixture.sql`.
Stalwart creates an account the first time a message arrives for it (`queryRecipient`), so users who never signed in
still receive mail (test T8). Passwords are argon2id exactly as Quant stores them
(`$argon2id$v=19$m=19456,t=2,p=1$...`, see `packages/auth/src/crypto/password.ts`). Switch back with `DIRECTORY=internal`
(plan 40 clears `directoryId`). Keep an administrator that does not live in the SQL directory in mind:
the bootstrap administrator is an internal account.

## Verified locally (laptop, no Docker)

The bootstrap settings and the plans in this folder were applied to a real Stalwart v0.16.27 (Windows binary:
bootstrap mode on a spare port, then normal mode) with `stalwart-cli`: all operations succeeded and re-applying was
idempotent. The Dns01, Http01, R2 and SQL-directory variants were each accepted by the server. Against that instance the scripts in `../lab/tests` passed: inbound delivery on 25, unknown recipient
rejected at RCPT, no open relay, authenticated submission on 587, delivery to the receiver, GTUBE flagged as spam
(Junk mailbox, `$junk`), IMAP login and fetch, JMAP discovery, Mailbox/Email/Thread calls, keyword and move
updates, EmailSubmission with HOLDUNTIL and cancel (undo send), blob upload/download, EventSource push, webhook
and MTA Hook payloads captured, and a 2,000 message run (2000/2000 delivered). What was **not** possible locally:
real DNS, ACME issuance, R2, the relay, port 25 from the internet and the SQL directory against Postgres. Those are
the lab steps L3 and L4.

## Notes and known limits

* `LAB_ALICE_PASSWORD` / `LAB_BOB_PASSWORD` must not contain `"` or `\` (they are put into JSON). If empty,
  `provision.sh` generates them into `.rendered/accounts.env`.
* Creating the ACME provider contacts the CA immediately; `ACME_CONTACT` must be a real, routable address.
* If a switch from `DIRECTORY=sql` back to `internal` reports one failed operation, run `./provision.sh apply` again.
* Stalwart's default inbound throttles (25 messages per hour per sender domain and recipient, 5 connections per second
  per IP) and its cap on messages per SMTP session (a client gets `452` and must reconnect) are sound for production. Plan 80 relaxes only the
  throttles, and only for the lab.
* The hooks stub accepts everything (`{"action":"accept"}`), and `tempFailOnError` is false so a stopped stub never
  blocks mail.
